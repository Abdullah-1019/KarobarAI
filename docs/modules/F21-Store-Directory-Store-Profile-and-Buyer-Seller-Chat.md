# F21 — Store Directory, Store Profile, and Buyer–Seller Chat

F21 is independent of the courier selection feature F20. This document describes the F21 scope and the currently implemented store profile increment. It does not change F20.

## Scope

F21 covers a public store directory, store profile metadata, editable AI store-description suggestions, separate human buyer–seller conversations, genuine AI chat streaming, profile-picture fixes, and restrained UI polish. Human conversations remain separate from AI chat sessions. Phase 3 adds persistent messaging; later increments address real-time synchronization, AI streaming, and avatars.

## Phase 3: persistent human messaging foundation

Human conversations use `human_conversations`, `human_messages`, `human_message_attachments`, and `human_conversation_reports`. They never use AI `chat_sessions` or `chat_messages`, and no human message is sent to Ollama or Gemini. One conversation exists per buyer and store; an optional live product reference is checked against that store at creation. Only active buyers can initiate a conversation. Active buyers and the owning seller can list, read, send, mark read, block, and report. All routes live under `/api/v1/human-chat`; the existing `/api/v1/stores/:slug/chat` remains the separate AI store assistant.

`POST /conversations` takes a store slug and optional product public ID. `GET /conversations` is paginated; `GET /conversations/:id/messages` uses a stable message cursor. `POST /conversations/:id/messages` accepts multipart `clientId` (UUID), optional text (up to 2,000 characters), and up to three images. The unique `(conversation_id, sender_id, client_id)` constraint makes retries idempotent. A successful send persists the message and one in-app notification in the same transaction. Read positions are persisted per participant; unread counts are derived from messages newer than that position. Phase 3 uses REST refresh, not Socket.IO read receipts or typing indicators.

Images are checked by file size and magic bytes, then stored under `human-chat/` in the existing private evidence bucket. The API returns attachment IDs, not object-storage URLs. A participant-only endpoint streams each image with `Cache-Control: private, no-store`; the frontend releases temporary blob URLs when no longer needed. Do not place these files in the public product-image bucket. The private evidence bucket must be configured for the backend before image sends can succeed.

The additive migration is `20261019020000_f21_human_chat_foundation`. It follows the F21 store-profile and Urdu-description migrations. Apply the full migration chain only to an explicitly identified database using Prisma's migration workflow; never reset the development database. ## Phase 4: real-time human chat delivery

### F21 chat experience update (19 October 2026)

The seller conversation list now uses the buyer's optional public display name, falling back to the localized “Buyer” label. A buyer may edit this name through the authenticated profile endpoint; email, phone, and internal IDs are not used as the display label. Migration `20261019030000_f21_buyer_display_name` adds a nullable `buyer_profiles.display_name` column. It was applied and checked only on the disposable `karobarai_f21_ux_isolated` database; this update did not migrate the development database. The earlier Urdu-description and human-chat migrations were applied to the local development database in a separately authorized operation before this update.

Human messages remain REST-persisted. An outgoing bubble shows **Sending** until its POST succeeds, then **Sent**. It shows **Seen** only after the recipient's persisted read position reaches that message. The read endpoint accepts an optional last-seen incoming message ID and checks conversation membership; the client advances it only while the conversation tab is visible. No **Delivered** indicator is shown: a socket broadcast does not establish recipient delivery. The `/human-chat` namespace accepts `typing:set` only for an authenticated, authorized participant who joined that room. Typing notices go only to the other room participant, expire after five seconds, and stop on send, blur, room leave, or disconnect. The frontend throttles typing notices and refetches authoritative REST state after reconnect. The messaging stylesheet uses the existing light/dark semantic color tokens.

The separate AI assistant has new browser-facing SSE routes for buyer-store and seller-assistant chat. The AI service streams actual Ollama `/api/chat` generation chunks and extracts only the user-facing `reply` string from the existing JSON envelope; tool-call JSON is withheld. The backend retains store context, retrieval, tool authorization, grounding, and final `chat_messages` persistence. The buyer assistant allows ordinary greetings and follow-ups without the former similarity-based scope refusal. A final `complete` event contains the saved authoritative answer. The existing non-streaming APIs remain available. A Stop action aborts the browser request, propagates cancellation to the backend and provider when supported, and does not persist an incomplete assistant message. Clients use a request UUID for retry; existing `chat_messages.id` values and a Redis lock prevent duplicate user/final-assistant rows and simultaneous processing of the same request. Tool side effects that complete just before a lost response are not yet transactionally resumable; clients must not interpret a transport retry as proof that a prior tool action did not occur.

Streaming is genuine model-level output for valid reply envelopes, not text split after generation. A malformed envelope falls back to the existing bounded non-streaming corrective call; that path emits only the final answer. Fast local replies and tool steps may likewise produce no visible intermediate text. Partial text is provisional until the final scoped and grounded answer is saved; the UI replaces it with the authoritative final response. Human conversations use none of these AI routes, models, tables, or events. Markdown is rendered through a restricted React component for paragraphs, lists, and code, with no raw HTML insertion.

A synthetic live check against the configured local Ollama model consumed a complete stream with two text deltas and one final envelope. This verifies provider-level incremental generation for that prompt; it does not establish authenticated browser behavior, latency under load, or every tool/RAG path. The first cold-load attempt timed out at 120 seconds. The completed check used a 360-second limit after the model loaded. The frontend production build completed with existing large-chunk/PWA precache warnings.

During a rolling local update, a Vite client can load before the API process reloads its new `/chat/stream` route. If the streaming request returns Express's HTML 404 for a missing route, the client retries through the existing non-streaming chat endpoint and displays only its completed reply. It does not synthesize incremental chunks or retry a structured API 404. Both routes share the same store/seller authorization rules. Full streaming becomes available after the API process runs the new routes. The buyer display-name migration must be applied before restarting that process on a database without the new column; verify a restorable backup first.

The existing HTTP server and Socket.IO dependency now host a separate `/human-chat` namespace. The client sends its short-lived access token in Socket.IO `auth.token`. The server verifies its signature, current account/role, Redis revocation entries, and expiration. Each `conversation:join` checks persisted buyer or owning-seller membership before joining a private room. A periodic session check disconnects revoked/expired sockets. The namespace never accepts a socket message-send event; `POST /api/v1/human-chat/conversations/:id/messages` remains the only send path and its 201 response is the sender acknowledgement. The existing transaction persists the message and notification before any socket notice is emitted. An idempotent retry returns the same message ID without another notice.

Event contracts (all events are change notices, not durable message bodies):

| Direction | Event | Payload | Meaning |
| --- | --- | --- | --- |
| Client to server | `conversation:join` | `{ conversationId }`, acknowledgement `{ ok: boolean }` | Join only after server-side participant authorization. |
| Client to server | `conversation:leave` | `{ conversationId }` | Leave the selected room. |
| Server to room | `message:created` | `{ conversationId, messageId }` | A new message was committed; refetch REST history. |
| Server to room | `read:changed` | `{ conversationId, readAt }` | A persisted read position advanced; refetch REST state. |
| Server to participant | `conversation:changed` | `{ conversationId }` | Refetch conversation list and unread counts. |

The frontend uses the existing REST queries for messages and unread counts. It does not append socket payloads to history, so a REST response and a broadcast cannot display duplicate messages. On every socket connection or reconnection it refetches the selected conversation and list to recover missed events. If the socket is unavailable, REST send/history remain usable and the page shows a live-update warning. This phase does not claim durable delivery receipts. Socket.IO rooms are currently process-local; multiple API workers would require a shared Socket.IO adapter before cross-worker delivery is reliable. No new Prisma migration is required for Phase 4. The Urdu-description and human-chat migrations were previously applied to the local development database; the buyer display-name migration remains pending and must not be applied until database recovery is verified.

## Increment 2: store profile fields

The existing `SellerProfile` remains one row per seller. It now has optional `storeCategoryId` referencing the actual `Category.categoryId` BigInt key, optional city, and JSON social links. The migration `20261019000000_f21_store_profile_fields` adds nullable category and city columns, a JSONB object with an empty default, a category index, and an `ON DELETE SET NULL` foreign key. Existing stores need no data backfill.

Sellers manage these fields through the existing `POST /api/v1/profile/me/store` onboarding endpoint and `PATCH /api/v1/profile/me` settings endpoint. Existing seller authentication and role authorization remain in force. The category must exist. City is limited to 80 characters. Facebook, Instagram, TikTok, and YouTube links require HTTPS and their respective domains; website links require HTTPS. Links are limited to 255 characters. WhatsApp accepts an international `+` number and is presented publicly as a safe `https://wa.me/` URL. Omitted fields remain unchanged on update; an empty city or social link clears it.

The existing public `/api/v1/stores/:storeSlug` response and page display category, city, member-since date, and populated social links. English and Urdu strings are provided. External links open with `noopener noreferrer nofollow`.

## Phase 1: public store directory

The public `GET /api/v1/stores` endpoint lists active, onboarded, non-deleted sellers with at least one live, non-deleted product. It accepts bounded `q`, `categorySlug`, `sort`, `page`, and `limit` query parameters. Search checks store name and description case-insensitively. Category filtering checks an existing product category slug and counts matching live products. Sort values are `name` (A–Z), `newest`, and `most_products`; each has a stable seller-key tie break. The response contains public branding, optional primary category and city, live product count, and pagination metadata. It does not select seller contact, financial, or account fields.

`GET /api/v1/stores/featured` returns up to eight newest eligible stores. Its public payload is cached in Redis under a versioned key for 45 seconds. Product moderation, seller suspension, or profile edits may remain stale in this featured section for at most that TTL; the paginated directory is uncached. There is no paid-featured flag, so “featured” currently means newest eligible stores.

The `/stores` page provides search, product-category filtering, sorting, pagination, loading, empty, and retry states. The homepage has a separate “Shop by Store” section with the same card destination and loading/empty/error handling. Both reuse the existing styling, English/Urdu translations, and RTL layout. Store social links remain part of the separate public store profile response; the directory does not expose them.

## Phase 2: bilingual store descriptions

The existing `seller_profiles.store_description` remains the English description, preserving older store data and API callers. Migration `20261019010000_f21_store_description_urdu` adds one nullable `store_description_ur` text column; no old value is overwritten or backfilled. Sellers edit either field through the existing authorized `PATCH /api/v1/profile/me` endpoint (2,000 characters maximum per field). Store onboarding remains compatible, and the public store profile, directory, and homepage select the description for the viewer's language, falling back to the other saved language when one is absent. Public text is rendered as React text, not HTML. The featured-store cache key advances to v3 so older payloads expire separately.

`POST /api/v1/profile/me/store/description-suggestion` is seller-only. The server resolves the caller's own onboarded store and its saved name, primary category, and city. An optional seller-entered business-details note (500 characters maximum) is sent only for this request. A category or business-details note is required to avoid generating generic claims from a store name alone. A Redis per-seller lock prevents overlapping requests and a per-seller window allows at most five requests per 15 minutes. Redis or provider failure leaves manual editing available. The endpoint returns `{ descriptionEn, descriptionUr }` and never saves it. The settings screen shows a preview; the seller explicitly applies it to editable fields, then separately selects Save. Generation never automatically replaces unsaved text.

The private AI service calls the **same configured Gemini API key and `GEMINI_LISTING_MODEL`** used for product image listing. No new key or model is required, and the unrelated Ollama chatbot and buyer–seller chat are unchanged. The Gemini request is text-only and asks for structured English and Urdu descriptions. The AI service validates output and uses bounded requests and retries; the backend validates it again. Store name, category, city, and any optional business-details note leave the deployment for hosted inference, so sellers should enter only facts they intend to share. Model output is an editable draft; sellers must review factual claims before publishing. No private account, wallet, or customer data is sent. The API does not return prompts, credentials, or provider response bodies.
