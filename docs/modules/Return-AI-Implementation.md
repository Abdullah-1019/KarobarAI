# Return AI: product listing and return photo comparison

## Status

**PARTIAL.** The DINOv2-Small checkpoint previously loaded and performed synthetic CPU inference. The inspection worker persists automatic decisions, and an exchange workflow is implemented with simulated return/replacement shipments. The updated exchange flow has not been verified in an authenticated browser, and real-world matching accuracy is unknown.

## Workflow

1. An authenticated buyer selects a delivered order item within the existing return window and a required reason code: WRONG_ITEM, DAMAGED, NOT_AS_DESCRIBED, CHANGED_MIND, or OTHER. OTHER requires a nonblank explanation.
2. The backend resolves the purchased order item and the first five product listing images in catalog position order. The buyer sees numbered references. No client-supplied image URL, category, or policy is trusted.
3. The buyer uploads exactly one private return photo for each displayed reference, in corresponding order and approximately the same angle. Index order cannot prove the angles match. If no listing image exists, the buyer supplies three photos for manual review without a similarity score.
4. On submission, the backend snapshots reference image IDs and URLs in inspection metadata, claims one BullMQ job, retrieves only URLs from its configured storage bucket, and sends bounded image bytes to the internal AI service.
5. DINOv2-Small produces a cosine similarity score for each numbered pair and a median overall indicator. Conflicting views or invalid evidence cause abstention. The scores are uncalibrated visual indicators, not identity probabilities, damage findings, or proof of physical product identity.
6. The backend independently checks the existing return policy, paired-photo counts, finite scores, and the median. With valid sufficient evidence, scores **>= 0.80** set APPROVED automatically, scores **>= 0.60 and < 0.80** enter MANUAL_REVIEW, and scores **< 0.60** set REJECTED automatically. Missing evidence, invalid results, model failure, or invalid configuration enter MANUAL_REVIEW. Automatic decisions never issue a refund or book a courier.
7. An AI-accepted return stays in the seller's active queue. The owning seller may reject it with a nonblank reason. The original AI decision and threshold snapshot remain in ReturnInspection.predictions, while AuditLog records the seller's identity, reason, and timestamp. The buyer can see the current status and override reason, and the existing decision notification is sent once after a successful status transition. A rejected buyer may use the existing appeal path.

The existing buyer routes are POST /api/v1/returns, POST /api/v1/returns/:id/images, POST /api/v1/returns/:id/submit, and GET /api/v1/returns/:id. Existing seller review/decision routes remain. Return AI **does not require dispatch or packing photos** and has no active dispatch-upload route or UI. Historical additive migrations retain a legacy DispatchEvidence model; migration history is preserved, but that model is not a comparison reference. The comparison itself needed no new migration: ReturnInspection.predictions JSON stores the reference snapshot and pair scores. The later exchange lifecycle adds a separate migration described below.

## Model and setup

- Official checkpoint: facebook/dinov2-small, revision ed25f3a31f01632728cabb09d1542f84ab7b0056, from https://huggingface.co/facebook/dinov2-small .
- The 88,249,960-byte model.safetensors was downloaded on 2026-10-14 into the Docker karobarai_dinov2_cache volume outside Git. It loads once per AI-service process for offline CPU inference.
- Download once: docker compose -f infra/docker-compose.yml run --rm --no-deps ai-service python -m app.llm.download_dinov2 . Start: docker compose -f infra/docker-compose.yml up -d ai-service . Readiness: GET /internal/return-comparison/health.
- Overrides: RETURN_DINO_MODEL, RETURN_DINO_REVISION, RETURN_DINO_CACHE_DIR, RETURN_DINO_MATCH_THRESHOLD, RETURN_DINO_MISMATCH_THRESHOLD, RETURN_DINO_MAX_SPREAD, RETURN_DINO_CPU_THREADS. See .env.example. No secret or model weight belongs in Git.
- AI-service display bands remain provisional (>= 0.90 LIKELY_MATCH; below that POSSIBLE_MISMATCH when evidence is valid). The **backend decision policy** uses `AUTO_ACCEPT_THRESHOLD=0.80`, `AUTO_REVIEW_THRESHOLD=0.60`, and `RETURN_AUTO_DECISIONS_ENABLED=true` by default. It fails closed to seller review if `0 <= review < accept <= 1` is violated or automation is disabled. The two model-side display bands are not business-decision thresholds. Every decision records its threshold snapshot and timestamp.

Missing/unreadable references, invalid return photos, model errors, absent checkpoint, and interrupted jobs fail to manual review without a fabricated score. Return evidence remains private with ownership checks and no-store responses. Product listing images use existing catalog storage. No Return AI image is sent to Gemini; separate Gemini product listing and Ollama chatbot/embeddings remain intact. Normal active-seller authorization applies; there is no Return AI subscription or admin approval gate.

## Evaluation and limitations

Run `python -m benchmarks.return_ai.evaluate` for the 13-case procedural fixture manifest; `--live` uses the cached model on available synthetic listing/return pairs. Historical fixture filenames retain `_dispatch` for reproducibility, but the manifest now identifies those files as listing references. When a manifest contains independently labeled `same_physical_product` booleans, the report calculates false acceptance, false rejection, and manual-review rates at the decision thresholds. The current illustrations are **not** independently labeled photos of same/different physical products, so these metrics remain null and real-world accuracy is unverified. A consented or licensed paired dataset grouped by physical product is needed before relying on automated rejection outside the demo.

The prior CPU smoke test used two synthetic pairs: unchanged 1.000000 and drawn stain 0.936620. Both were LIKELY_MATCH, showing that small defects may retain high global similarity. Those results preceded this numbered-pair API correction and do not verify the browser flow. Product listings may change while a buyer fills the form; references are snapshotted on submission. If the object is later unavailable, comparison falls back to manual review.

## Exchange and operations extension (2026-10-15)

The canonical `Return.status` remains the decision/acceptance state. The BullMQ inspection worker conditionally moves only `UNDER_AI_REVIEW` to `APPROVED` at scores >= 0.80, `MANUAL_REVIEW` at 0.60 to below 0.80, or `REJECTED` below 0.60. Invalid evidence, unavailable inference, ineligible cases, and invalid scores enter review. The worker records the threshold snapshot and decision in `ReturnInspection.predictions` and an audit entry in the same transaction. `RETURN_AUTO_DECISIONS_ENABLED=true` is the intended demo setting; the active process must load that environment setting and be restarted after changing it. A seller decision cannot be overwritten by a late inspection result. Middle-band and exceptional cases appear in the owning seller's queue. The owning seller can override an AI acceptance only before a return booking claim, with a nonblank reason; the AI decision remains in the inspection record.

The new migration `20261015000000_return_exchange_lifecycle` creates a stable `orders.order_number` sequence and backfills existing orders in placement order. It adds `buyer_confirmed_at`, per-item `resolution`, `return_fulfillments`, and separate `return_shipments` and `return_shipment_events` with a unique `(return_id, leg)` key. Existing approved returns receive an unbooked fulfillment row; no historical shipment is fabricated. Apply only through the normal reviewed Prisma migration procedure after a database backup. This migration was first applied to disposable PostgreSQL on loopback port 5547; it was later applied to the local Docker development database before the four subsequent migrations described below.

Operational flow:

1. An accepted return appears in the owning seller's queue. That seller explicitly posts `/api/v1/seller/returns/:id/book-return-courier`. Only mock mode is supported. The service evaluates the existing courier quotes, prefers the eligible outbound carrier, and otherwise books the highest-scored eligible candidate. No other candidate is booked. A prior booking claim prevents duplicate external calls. A confirmation timeout or unknown booking result remains `UNCERTAIN` for reconciliation; the API never claims booking succeeded without a persisted result.
2. A recurring five-minute mock tracking poll advances separate return and replacement legs one step at a time using conditional status updates. Simulated events and bookings are labeled as such. No real courier API or TCS account is used. The static Karachi depot and synthetic weight/quote profile are the existing simulator's assumptions, not real origin or ETA data. Legacy admin simulator routes remain for compatibility, but are not required by the normal seller/buyer flow.
3. After the return leg reaches the seller, the owning seller posts `/api/v1/seller/returns/:id/confirm-receipt` with `RESELLABLE`, `DAMAGED`, or `NEEDS_INSPECTION`. Only `RESELLABLE` restores sellable stock, inside the same transaction as the receipt record. Replayed receipt actions cannot restore stock twice. `DAMAGED` retains the item outside sellable stock. The order item becomes `RETURNED`; the original outbound order and shipment history are preserved.
4. The seller selects a replacement product in the same store through `/api/v1/seller/returns/:id/replacement`. Stock is reserved with the catalog's conditional decrement in a transaction and cannot be reserved twice. The seller records packing through `/api/v1/seller/returns/:id/replacement/pack` before booking a separate simulated replacement through `/api/v1/seller/returns/:id/book-replacement`. Courier delivery sets `REPLACEMENT_DELIVERED` and retains item resolution `RETURNED`. Only the owning buyer's `/api/v1/returns/:id/replacement/confirm-receipt` changes fulfillment to `EXCHANGE_COMPLETED` and item resolution to `EXCHANGED`.
5. If exchange is not possible after receipt, the seller can POST `/api/v1/seller/returns/:id/refund-proposal` with a reason. Only the owning buyer can POST `/api/v1/returns/:id/refund-proposal/respond`. Consent and decline are persisted separately. Decline allows the seller to resume replacement selection. **No payment adapter is called and no refund is reported as issued.** Buyer consent leaves `REFUND_CONSENTED` for authorized manual processing because an integrated return-specific, consent-gated refund processor has not been implemented.
6. A buyer may POST `/api/v1/orders/:id/confirm-receipt` only after outbound delivery. This records `buyer_confirmed_at` and moves the order to canonical `COMPLETED`; a repeat is idempotent. This original-order state remains historical after an item is returned/exchanged. Buyer, seller, and admin order/return lists use the stable display number while links continue to use the order public ID.

The buyer's My Returns page uses persisted status, shipment events, receipt/replacement state, and refund proposal data. Provider internals and raw similarity scores are omitted from buyer detail responses. Authorized seller/admin pages retain the stored score and paired images; the seller view shows a compact static 0.60/0.80 comparison scale. The current in-app notification queue is used for decision, review, courier, receipt, proposal, response, and replacement milestones; queue delivery requires the normal notification consumer.

The default 0.60/0.80 boundaries are provisional and have **no independently measured real-world false-acceptance or false-rejection rate**. Lighting, angle, crop, folds, and similar products can change the score. The DINOv2 score is not a probability or proof of identity. No refund or courier booking is triggered by the visual comparison itself. No authenticated browser journey or real courier integration has been verified for this extension. The outbound order now persists `PROCESSING`, `PACKED`, and `HANDED_OVER_TO_COURIER` separately; courier booking leaves it `PACKED` until seller handover.
The current catalog stores sellable quantity per product, without a separate variant-level stock ledger; replacement reservations follow that existing product-level model. A physical warehouse/location and real courier ETA are not represented. Consent to a refund has no automatic payment execution path in this extension.

Migration `20261015130000_seller_return_exchange_flow` adds appeal reason and buyer replacement-receipt timestamp/state. Migration `20261015150000_replacement_packing` adds a separate packed replacement state and timestamp. Migration `20261015160000_item_scoped_returns` replaces one-return-per-order uniqueness with one-return-per-order-item uniqueness. These forward-only migrations were first applied to disposable PostgreSQL on loopback port 5547 for testing. On 2026-10-15, after validating a private backup archive and confirming the target was the local Docker development database `karobarai`, all four were also applied there with `prisma migrate deploy`. Prisma reported the schema up to date, and authenticated read-only requests to `GET /api/v1/seller/returns` and `GET /api/v1/seller/returns/550` both returned HTTP 200. The return row count remained 13 before and after. This does not verify the full authenticated browser workflow.

- A buyer's one-time return window begins at `orders.buyer_confirmed_at` and closes 24 hours later. The order must be `COMPLETED`. Each purchased order item can be returned once, even if an earlier item was rejected. Legacy item-less returns block further requests for that order because their item cannot be established safely.
- The settlement poll now uses the same buyer-confirmed 24-hour cutoff and waits until every item-level return on the order is closed. The older `return_window_days` configuration row is retained for migration compatibility but does not change this fixed FYP policy.
- An AI or seller rejection can be appealed once with a nonblank buyer reason. The appeal appears in the owning seller's queue. That seller resolves it with a reason; acceptance enters the accepted-return flow, while rejection closes the appeal. The original AI decision and later human action remain in the inspection record and audit history. Normal review and appeal resolution do not require an administrator.
- Seller-approved review and appeal cases remain in the active seller queue while awaiting return-courier booking. The order detail API marks each purchased item independently eligible or ineligible for return, and the buyer return form disables only ineligible items.
- Each My Returns link now includes its own return ID so two returned items from one order open separate details. The legacy order-only detail URL remains for existing bookmarks and resolves the first matching return.
- The owning seller books only simulated reverse courier shipments and confirms physical receipt and condition after simulated delivery. Sellable stock is restored only after a resellable condition decision. The seller reserves replacement stock, records packing, then books a separate simulated replacement leg. The exchange completes only after buyer confirmation of replacement receipt.
- For the original outbound order, the seller can mark processing, packed, handover, and simulated courier delivery in sequence. The delivery action requires a booked simulated shipment and creates one order/tracking milestone; it does not confirm buyer receipt, complete the order, or mark COD money collected. The buyer's separate receipt confirmation completes the order and, for this seller-reported COD path, confirms the pending COD payment. A seller-reported delivery is excluded from measured courier on-time performance.
- The seller may propose a refund after receipt when exchange cannot proceed. Buyer consent or refusal is stored; consent does not execute a Stripe or other payment refund. Operational refund processing remains a separate, unsupported step.
- The order and return pages read canonical persisted status. The buyer's My Returns page shows the appeal, reverse leg, replacement leg, and refund proposal. The seller page shows review/appeal actions and fulfillment actions based on persisted state. No authenticated browser journey has yet verified this complete flow.
- In-app notifications inform the owning seller of an AI accept/reject decision and the buyer when replacement stock is reserved. Notification delivery depends on the existing notification worker; a database transition remains authoritative if queue delivery is unavailable.
